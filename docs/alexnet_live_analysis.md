# Наблюдение за работающим обучением AlexNet

Дата: 20 октября 2026, около 18:23–18:25 МСК.
Mac: Apple M1 Pro, 16 ГиБ RAM. Ноутбук использует MPS, batch_size=512,
четыре постоянных workers DataLoader.

## Как проводилось наблюдение

Использованы системные счётчики CPU, памяти и GPU, а также короткое
статистическое семплирование стеков основного процесса и одного worker
через macOS `sample`: 5 секунд с интервалом 10 мс.

Kernel не прерывался и не перезапускался. Код, состояние модели и
DataLoader не изменялись; команды в работающий Jupyter kernel не отправлялись.
Дополнительное обучение и GPU-бенчмарки параллельно не запускались.
У системного семплирования есть небольшая диагностическая накладная стоимость.

Найдены основной kernel PID 32893 и его четыре workers:
32921, 32922, 32923, 32924. Во втором Jupyter kernel активной нагрузки
в исходном наблюдении не было.

## Наблюдения

| Показатель | Результат |
|---|---|
| Загрузка GPU всего устройства | 96–100%, восемь наблюдений примерно за 14 секунд |
| CPU основного kernel | Примерно 1,9–5,2% одного ядра в пяти двухсекундных интервалах |
| CPU каждого worker | Примерно 0–3,1% одного ядра в тех же интервалах |
| Главный поток kernel в sample | 358 из 370 выборок, около 97%, в `.item()` → ожидание завершения MPS/Metal |
| Главный поток одного worker | 381 из 391 выборки, около 97%, в `poll` при ожидании данных очереди |
| Physical footprint kernel из sample | Около 6,5 ГБ, пик около 6,6 ГБ |
| Используемая память GPU по системному счётчику | Примерно 6,6–7,2 ГБ |
| Выделенная драйвером память GPU по системному счётчику | Примерно 10,8–11,1 ГБ |
| Занятый swap всей системы | Примерно 4,3 ГБ |

GPU-счётчики и swap относятся ко всей системе. Их нельзя целиком приписать
AlexNet. Footprint kernel измерен отдельно для процесса обучения.
RSS процесса здесь не отражает весь расход памяти: он был гораздо меньше
его footprint и не учитывает память обучения так, как требуется для оценки
общего давления на unified memory.

За окно 14,28 секунды системные счётчики изменились так:

- Swapins: +3011 страниц, около 49 МБ при странице 16 КиБ.
- Swapouts: без роста в этом окне.
- Compressions: +196247 страниц, около 3,22 ГБ обработанных страниц.
- Decompressions: +140054 страниц, около 2,29 ГБ обработанных страниц.

Это объём событий обработки страниц, включая повторную обработку тех же
страниц, а не столько новой занятой памяти. Обмен с диском не является
непрерывной записью гигабайтов за секунду, но активность подсистемы памяти
не сводится к swap, оставшемуся от старых процессов.

## Где находится ограничение

Подготовка данных успевает за моделью: workers мало используют CPU,
семплированный worker преимущественно ждёт новых заданий, а основной
процесс преимущественно ожидает GPU. Это согласуется с тем, что очередь
подготовленных батчей успевает наполняться.

Основное ограничение в этом окне — выполнение модели на GPU/MPS,
включая работу с памятью. Дополнительный фактор — давление на общую
память системы и активное сжатие/восстановление страниц.

По этим наблюдениям нельзя разделить GPU-время на арифметику,
пропускную способность памяти, отдельные слои и временные буферы.
Также нельзя оценить точный процент замедления из-за памяти.
Для этого нужен отдельный контролируемый прогон с профилировщиком.

### Почему стек указывает на item()

Наблюдалась цепочка:

```text
Tensor.item()
→ _local_scalar_dense_mps
→ mps_copy_
→ MPSStream::synchronize
→ MTLCommandBuffer waitUntilCompleted
```

В текущем цикле `.item()` извлекает loss и число правильных ответов
на каждом батче. В этой точке CPU ждёт ранее поставленных GPU-операций.
Около 97% выборок в таком стеке не означает, что само преобразование
скаляра потребляет 97% времени или что его удаление даст такое ускорение.
Ожидание включает работу модели, backward и оптимизатора на GPU.

## Почему выигрыш меньше, чем у LeNet

Изменения ускоряли подготовку данных. Вычислительная стоимость AlexNet
намного выше, поэтому оставшаяся работа модели занимает большую долю
времени эпохи. Четыре workers теперь могут готовить следующие батчи,
пока GPU выполняет предыдущий.

Аналитическая оценка свёрток и линейных слоёв по коду ноутбуков:

| Модель | MAC на изображение, forward |
|---|---:|
| LeNet | 651 720 |
| AlexNet | 360 352 256 |

MAC — умножение с накоплением. Разница составляет примерно 553 раза.
Оценка не включает backward, функции активации, pooling и LocalResponseNorm
и не является отношением реального времени обучения.

В AlexNet вторая свёртка 96→256, kernel 5×5, карта 16×16 даёт
157 286 400 MAC на изображение: около 44% указанного арифметического
объёма forward. Это кандидат для отдельного измерения времени, но его
фактическое доминирование по задержке не установлено.

Даже выход первой свёртки при батче 512 имеет
512×96×32×32 float32-элементов — около 201 МБ. В обучении дополнительно
нужны другие активации, градиенты и временные буферы. Два слоя
LocalResponseNorm также следует включить в будущий разбор по операциям.

Ускорение около двух раз, сообщённое пользователем, совместимо с этой
картиной. До оптимизации здесь не было записано сопоставимого профиля,
поэтому точно восстановить доли старого времени нельзя. В частности,
нельзя из одного коэффициента ускорения вывести, что CPU раньше занимал
ровно половину времени: часть работы теперь перекрывается.

## Что проверять в следующем прогоне

1. Сравнить batch_size=128, 256 и 512 после прогрева: изображения в секунду,
   время эпохи, давление на память и качество. Больший батч здесь уже
   нельзя считать предпочтительным только потому, что он не вызывает OOM.
2. Отдельно измерить свёртки, LocalResponseNorm, backward и шаг Adam
   средствами MPS-профилирования. Не делать это дополнительным GPU-прогоном
   параллельно с текущим обучением.
3. Проверить накопление метрик на устройстве и извлечение скаляров в конце
   эпохи. Это может уменьшить синхронизации, но не уберёт стоимость GPU-работы.
4. Сравнить расход памяти при меньшем числе workers, если память остаётся
   ограничением. По текущему низкому CPU workers наращивать их число
   не обосновано.

В текущий запуск перечисленные изменения не внесены.
