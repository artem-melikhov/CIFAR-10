# Где AlexNet теряет время на PyTorch/MPS

## Условия

Исследована текущая AlexNet из `notebooks/AlexNet.ipynb` на Apple M1 Pro, 16 GiB, PyTorch 2.14.1, MPS. Пользователь подтвердил, что речь о PyTorch/MPS. MLX в этом проекте не используется.

Замеры выполнялись отдельными процессами последовательно, без конкурирующих GPU-бенчмарков. Рабочий notebook, архитектура в нём и сохранённые веса не изменены. Эксперименты загружают копию checkpoint `notebooks/models/alexnet.pth` и не сохраняют обучение поверх него.

Для изолированных замеров: batch 256, FP32, Adam 3e-4, настоящие CIFAR-10 из фиксированного набора, три прогревочных шага, медиана семи последующих. Вход уже стандартизирован и находится на MPS: этим исключены DataLoader, CPU augmentation и передача данных из измерения вычислений модели. Синхронизация на границах forward/backward/optimizer позволяет дождаться настоящего выполнения GPU.

## Результат: два крупных источника затрат

Обычный шаг: **285,0 мс**, из них forward + loss 83,2 мс, backward 197,0 мс, Adam 4,7 мс. Главная часть времени — backward.

Послойная диагностика:

| Участок | Forward, мс | Backward, мс | Всего, мс |
|---|---:|---:|---:|
| Conv 3→96, 3×3 | 1,8 | 12,1 | 13,8 |
| Первый LocalResponseNorm | 17,1 | 33,4 | 50,5 |
| **Conv 96→256, 5×5** | **24,9** | **65,5** | **90,4** |
| Второй LocalResponseNorm | 11,8 | 21,5 | 33,2 |
| Conv 256→384, 3×3 | 5,6 | 16,4 | 22,1 |
| Conv 384→384, 3×3 | 8,1 | 23,1 | 31,3 |
| Conv 384→256, 3×3 | 5,7 | 16,5 | 22,1 |

Все свёртки вместе — около 180 мс, два LRN — около 84 мс. В инструментированном шаге это около 59% и 28% соответственно. Хуки и синхронизация после каждого слоя увеличивают шаг до 303,7 мс (+6,5% к обычному); кроме того, для корректного измерения backward первой свёртки включён градиент входа. Поэтому это оценка распределения времени, а не точное разложение обычных 285 мс. Независимые эксперименты ниже подтверждают вклад LRN без послойных хуков.

Вторая свёртка выполняет около 157 млн MAC на изображение — примерно 44% всех MAC модели. Это объясняет её большой вклад, но вывод о времени сделан по измерениям, а не только по FLOPs.

## Независимая проверка и варианты ускорения

| Вариант | Шаг, мс | Изменение времени к исходному |
|---|---:|---:|
| Исходная модель | 285,0 | — |
| Отключён только первый LRN | 235,7 | −17,3% |
| Отключён только второй LRN | 252,6 | −11,4% |
| Отключены оба LRN | 203,9 | −28,5% |
| Эквивалентный LRN через avg_pool2d | 258,9 | −9,2% |
| Эквивалентный LRN через сумму сдвигов | 287,4 | +0,8% |
| **Эквивалентный fused Metal LRN** | **215,5** | **−24,4%; скорость ×1,32** |
| Исходная модель с channels_last | 506,1 | +77,6% |

Отключение LRN — только диагностическая абляция: оно меняет функцию модели. Нельзя переносить сохранённую accuracy на такую модель или обещать качество после обучения с удалёнными слоями.

`channels_last` для текущей комбинации слоёв и backend ухудшил результат. Это измерение всей модели, а не доказательство, что каждая отдельная свёртка в этом формате медленнее.

## Почему LRN оказался дорогим

Установленный `torch.nn.functional.local_response_norm` реализует LRN цепочкой операций: квадрат входа, reshape/pad, `avg_pool3d` по каналам, масштабирование, степень, деление. Autograd затем выполняет обратные операции. Здесь обрабатываются большие активации: первый LRN получает `[256, 96, 32, 32]`, около 96 MiB FP32 только для одного тензора.

Это **LocalResponseNorm внутри модели**, а не входная стандартизация `(image - mean) / std`. Оптимизация uint8 и CPU preprocessing не устраняет его стоимость. Измеренный выигрыш fused-варианта относится ко всей цепочке операций LRN; приписывать весь выигрыш только `avg_pool3d` без дополнительной детализации было бы неверно.

Экспериментальный `benchmarks/alexnet_metal_lrn.py` вычисляет тот же LRN одним Metal kernel для forward и одним для backward. Для нечётного окна:

```
a = alpha / size
s_i = k + a * sum(x_j**2 for j in channel_window(i))
y_i = x_i * s_i**(-beta)
dx_i = g_i * s_i**(-beta)
       - 2*a*beta*x_i * sum(g_j*x_j*s_j**(-beta-1) for j in channel_window(i))
```

На границах каналов сумма дополнена нулями, делитель остаётся `size`, как в исходной реализации.

## Проверка эквивалентности

Для LRN2D и MetalLRN проверены выходы и градиенты входа при размерах `(2,7,4,4)`, `(2,96,32,32)`, `(2,256,16,16)` и масштабах случайного входа 1, 10, 100. Все сравнения прошли заданные допуски. Полные численные результаты: `benchmarks/alexnet_bottleneck/equivalence.json`.

Сохранённый checkpoint проверен на всех 10 000 validation-изображениях:

| Реализация | Accuracy | Cross entropy | Изменившиеся предсказания |
|---|---:|---:|---:|
| Исходная | 77,61% | 0,6704727144 | — |
| LRN2D | 77,61% | 0,6704727144 | 0 |
| MetalLRN | 77,61% | 0,6704727054 | 0 |

Это проверка эквивалентности на checkpoint и локальных градиентах. Полное обучение до сходимости не выполнялось: из-за округления FP32 траектории длительного обучения могут расходиться даже у математически эквивалентных реализаций.

Экспериментальный Metal kernel поддерживает **MPS, FP32, NCHW, нечётный размер окна**, как в текущей модели. Он не подготовлен для AMP, высших производных, torch.compile или произвольных backend. В рабочую модель автоматически не подключён.

## Почему дальнейшая оптимизация CPU мало помогает

Предыдущий анализ действующего обучения показал, что CPU workers преимущественно ожидают очередь, а основной процесс ждёт завершения MPS на `.item()`. Теперь изолированный шаг с готовыми MPS-входами занимает примерно столько же, сколько шаг настоящего обучения с preprocessing: вычисления модели объясняют почти всё время.

`.item()` является местом ожидания уже поставленных в очередь GPU-операций. Его длительность нельзя трактовать как независимую стоимость получения одного числа или обещать соответствующее ускорение его удалением.

Больший batch ранее перестал давать выигрыш между 256 и 512, а 1024 вызвал сильное давление на память. AMP FP16 ранее дал лишь около 2,5% в коротком эксперименте, BF16 замедлил обучение. Увеличение batch и смена dtype сами по себе не устраняют измеренную стоимость текущих свёрток и LRN.

## Настоящий DataLoader + AutoAugment: результат

Дополнительно проведён последовательный прогон каждой реализации с реальными 40 000 train-изображениями, четырьмя workers и онлайн-аугментациями. Первые восемь батчей исключены как прогрев; оставшиеся 37 952 изображения измерены вместе с получением батча, переносом, стандартизацией, forward/backward/Adam и двумя `.item()` для метрик. Последний батч неполный.

| Вариант | Время 37 952 изображений, с | Изображений/с | Ожидание DataLoader, с |
|---|---:|---:|---:|
| Исходный | 42.812 | 886.5 | 0.077 |
| MetalLRN | 32.508 | 1167.5 | 0.072 |

**Выигрыш полного train-конвейера: скорость ×1.317, время −24.1%.** Ожидание выдачи готовых батчей составляет 0.18% исходного времени и 0.22% после ускорения. CPU-аугментации выполняются параллельно и практически полностью скрыты вычислениями GPU. Это замер одной эпохи на вариант после короткого прогрева, а не статистика нескольких полных повторов; графики, checkpoint save и validation в него не входят.

Приоритет: эквивалентная оптимизация LRN даёт уже измеренный выигрыш без удаления слоёв. После неё основной оставшийся объект оптимизации — свёртки, особенно 96→256 5×5. Замена архитектуры этой свёртки, уменьшение каналов или удаление LRN требуют отдельного переобучения и проверки качества.

## Детализация backward первого LRN

Дополнительный запуск на `[256,96,32,32]` с хуками отдельных узлов autograd показал: backward `avg_pool3d` — около 9,1 мс, деления — 8,2 мс, степени — 5,0 мс, padding — 4,4 мс. Forward LRN — 17,3 мс, инструментированный backward — 35,7 мс. Значит, стоимость распределена между pooling и несколькими проходами по большим тензорам; одной заменой pooling невозможно убрать все затраты. Эти измерения также включают дополнительную синхронизацию и служат для атрибуции, а не для оценки обычной скорости. Исходные данные: `lrn_operators.json`, скрипт: `benchmarks/alexnet_lrn_operators.py`.

## Дополнительное объяснение слабого выигрыша AMP

Хуки фактических dtype при `torch.autocast('mps', dtype=torch.float16)` подтвердили: Conv/ReLU выдают FP16, но каждый LocalResponseNorm возвращает FP32, а следующий MaxPool2d также работает с FP32. Далее свёртка снова выдаёт FP16. Два крупных LRN и следующие pooling поэтому не становятся полностью FP16 при включении AMP, и возникают переходы между dtype. Это одна подтверждённая причина, почему AMP не ускоряет всю модель пропорционально уменьшению разрядности. Она не доказывает, что остальные причины исключены или что MPS-свёртки обязаны ускоряться вдвое. Полный список: `amp_dtypes.json`.
